# 계정 유지와 새 세션 배정: 설계 보완안

상태: D20(2026-10-20)으로 전환 정책과 분산 기본값이 승인되었다. 구현 규칙은 contract C7–C7.2와 C12가 정본이며, 이 문서는 배경과 예측 기능의 관측 전용 한계를 설명한다.

## 1. 서로 다른 세 가지 문제

| 문제 | 의미 | 다른 계정으로 바꾸면 |
|---|---|---|
| 대화 재개 | 클라이언트가 저장한 대화 이력을 다시 사용한다 | 원래 기록이 있어도 모든 상류 항목의 호환성을 보장하지 않는다 |
| 프롬프트 캐시 | 이전 입력을 다시 계산하는 양을 줄인다 | 계정 간 적중을 가정하지 않는다 |
| 이전 추론·압축 상태 | 서명된 thinking이나 암호화된 reasoning/compaction 등을 다시 사용한다 | 모델·계정·서비스 경로에 따라 무시되거나 거절될 수 있다 |

Claude Code는 로컬 대화 기록을 저장하고 재개한다. Messages API는 호출자가 대화 이력을 보내는 구조다. 이 두 사실만으로 다른 계정에서 모든 상태가 유지된다는 결론을 내리지 않는다. [Claude Code 세션](https://code.claude.com/docs/en/sessions), [Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages).

Claude API는 조직·워크스페이스 경계에 캐시를 분리한다. 이는 Claude 구독 OAuth 계정 사이의 캐시 공유를 보장하는 규칙이 아니다. 계정을 유지해도 입력·모델·추론 설정이나 캐시 수명이 달라지면 적중하지 않을 수 있다. [캐시 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

현재 공식 문서는 Sonnet 5.5·Haiku 5.5가 만든 thinking을 원래 계정 또는 연결 계정에서만 사용할 수 있다고 설명한다. 다른 계정에서는 이를 버리고 요청을 처리한다. prefix 변경에 대한 검증과 모델 간 호환성은 별도다. 이 API 설명을 Opus의 모든 버전, 구독 OAuth 경로 또는 Codex에 일반화하지 않는다. quota-baton은 호환성을 만들기 위해 본문이나 서명을 수정하지 않는다. [Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking), [Preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking).

과거 V2의 성공은 시험한 모델·인증 경로·이력 형태·전송 방식에 한정된 증거다. 향후 모든 계정 전환의 성공 또는 무손실을 보장하지 않는다. 현재 캐시 적중률도 계정 전환의 이익을 증명하는 실험 대조군이 아니다.

## 2. 전환 권한과 배정 정책을 분리한다

새 세션은 여유와 초기화 시각을 보고 계정을 고른다. C5 부적격으로 옮기는 그룹도 새 계정의 placement로 계산하여 D20 charge와 cap을 적용한다. cap은 강제 복구를 거부하지 않으며, 적격 계정이 있으면 전환할 수 있다. 이미 적격 계정을 사용하는 루트 세션은 그 계정을 유지한다. 사용량 예측이나 새 배정 순서가 기존 세션의 이동 권한을 넓히지 않는다.

승인된 선택은 strict(계정 유지), recover(사용 불가 시 전환), rebalance(분산 허용)이며 기본값은 rebalance다.

| 선택 | 같은 계정의 정상 처리 | 사용량 소진·최종 인증/결제 문제 | 지속 속도 제한에 따른 분산 |
|---|---|---|---|
| 계정 유지 | 유지 | 대기 예산 안에서 같은 계정 복구 후 멈춤 | 하지 않음 |
| 사용할 수 없을 때 전환 | 유지 | 허용된 다음 요청 경계에서 제한적으로 전환 | 별도 허용 필요 |

속도 제한으로 분산하는 권한은 별도로 둔다. 추가 유료 크레딧 사용 권한도 별도로 둔다. 가용성을 선택했다고 두 권한을 자동으로 켜지 않는다.

`계정 유지`는 계정 ID를 바꾸지 않는다는 약속이다. 토큰 갱신, 같은 계정 재로그인, 연결 재수립은 허용한다. 응답 성공이나 캐시 적중을 약속하지 않는다. 계정이 삭제·중지되거나 인증·결제 문제로 사용할 수 없으면 다른 계정으로 조용히 옮기지 않고 이유를 보여 준다.

정책의 우선순위는 전역 기본값, 프로젝트의 명시적 선택, 루트 세션의 명시적 선택 순이다. 자식 에이전트는 루트의 정책과 계정을 상속한다. 계정 중지·인증 안전성·크레딧 금지 등 강제 제약은 어떤 세션 정책도 해제하지 못한다.

표시용 폴더 이름이나 `x-quota-baton-label`을 프로젝트 식별자 또는 전환 권한으로 사용하지 않는다. 로컬에 등록한 불투명한 프로젝트 ID를 사용하고, 디렉터리는 이를 찾는 위치 정보로만 다룬다. 복제·worktree·이름 변경 시 같은 프로젝트로 묶을지는 명시적으로 연결한다. 저장소 안의 파일만으로 지출·전환 권한을 확대하지 않는다.

루트의 정책·출처·revision·고정 계정과 필요한 이동 예산은 재시작과 takeover에 보존한다. 일반 바인딩 LRU에서 사라졌다는 이유로 `계정 유지`를 잊지 않는다. 새 기본값은 원칙적으로 새 세션에 적용하고, 기존 세션의 허용 범위를 바꾸는 작업은 별도로 표시한다. 금지·권한 철회는 아직 전송하지 않은 요청에 적용한다.

## 3. 대기와 전환

구독 사용량 소진과 짧은 요청 속도 제한은 별도다. 불명확한 429를 계정 전체의 구독 소진으로 단정하지 않는다. 상태 코드와 구조화된 오류 신호가 충돌할 때의 우선순위도 명시적으로 검증한다.

60초 reset hold는 캐시 손실 대신 기다릴 수 있는 운영 기본값이다. 서비스가 요구하는 시간이나 캐시 보존 보장이 아니다. 대기 규칙은 contract C6.3·C7·C7.2가 정본이며 다음 조건을 따른다.

- 세션 정책별 대기 한도를 표시한다. `0`은 초기화를 기다리지 않는다는 뜻이다.
- 실제 제한을 일으킨 window와 신뢰할 수 있는 최신 reset 근거만 사용한다. 오래되거나 합성한 cooling 만료를 실제 reset처럼 쓰지 않는다.
- 가능하면 상대 시간을 수신 시 monotonic deadline으로 바꾼다. 절대 시각은 clock 오차를 고려한다.
- reset 대기, rate 대기, 연결, 갱신, 재시도를 하나의 요청 전체 시간 예산 안에 넣는다. WS upgrade는 클라이언트 연결 timeout보다 충분히 짧아야 한다.
- 같은 reset 증거에 대해 무한히 다시 기다리지 않는다. 확인 요청을 묶고, 실제로 초기화되지 않았으면 정책에 따라 전환하거나 오류를 보여 준다.
- 취소·중지·정책 철회 시 기다리는 요청을 깨운다. 전송 직전에 최신 적격성과 권한을 확인한다.
- rate hold 한도 안에서는 서버의 재시도 권고와 계정별 pacing을 따른다. 한도 만료 시에는 D14·D20 §4의 같은 계정 한 번 전송 규칙을 적용하고 이후 rate 재시도를 끝낸다.

초기화 대기는 기본 60초이며 루트 정책으로 0–120초를 설정한다. D20 §4는 초기 admission뿐 아니라 HTTP retry와 WS resend·redial의 rate hold 만료에도 같은 계정에 한 번 보내는 D14 규칙을 유지한다. HTTP pre-commit 전체 경로에는 기본 300초 deadline과 만료 시 504가 적용되며, 이미 공개한 응답 스트림은 끊지 않는다. WS upgrade는 refresh와 dial을 포함한 기본 10초 전체 envelope를 사용한다. 두 deadline은 D20 §4로 승인되었다.

## 4. 계정 왕복과 이동 비용

D20의 재량적 이동 보호는 그룹별 체류·재방문 제한과 그룹·제공자별 이동 예산을 함께 적용한다. 요청당 서로 다른 계정 4개 제한과 계정별 이동 표시 예산은 별도다. C5 강제 이동은 이력에 기록하지만 재량적 이동 예산을 사용하거나 그 예산으로 거부되지 않는다.

지속 속도 제한의 재량적 이동에는 다음 상태를 사용한다.

1. 루트 그룹별 최소 체류 시간, 최근 떠난 계정의 재방문 유예와 시간 구간별 재량적 이동 횟수.
2. 그룹별·제공자별 재량적 이동 예산. D20 §4로 도착 후 대기 보호는 제거되었다.
3. 대상 계정의 적격성, gate, 알려진 최신 quota와 예약을 합산한 여유, D20의 증거·cap 판단. 관측 부족은 여유가 확인됐다는 뜻이 아니다.
4. 이동 표시를 만들 때와 실행할 때 각각 현재 조건을 확인한다. 동시 이동과 새 배정이 사용할 도착지의 여유를 원자적으로 예약한다.
5. 임계값이 다른 계정 사이의 비교 기준을 명시한다. 단순 대화 개수와 정규화한 부하를 섞지 않는다.
6. 마지막 작은 WS delta를 다음 전환의 full-input 재전송 비용으로 보지 않는다. 비용을 모르면 재량적 이동을 억제한다.
7. 남은 재량적 보호가 이동을 막으면 현재 계정을 유지하고 유효한 overload 표시도 보존한다. 이를 강제 이동으로 바꾸지 않는다. 대안에서도 제한이 반복되거나 예산이 끝나면 더 옮기지 않는다. 캐시를 되찾겠다는 이유로 원래 계정으로 자동 복귀하지 않는다.

이 제한의 수치는 운영 휴리스틱이다. 제공자 용량이나 캐시 TTL의 사실로 쓰지 않는다. 확정 인증 장애처럼 이동이 필요한 복구와 선택적인 부하 분산은 사유·예산을 구별하되, 실제 전체 전송과 이동 증폭은 함께 관측한다.

## 5. 초기화 전에 남은 사용량 활용

현재 90% gate는 새 세션의 우선 배정 기준이다. 사용 중인 계정을 90%에서 중단하는 기준이 아니다. 모두 gate를 넘더라도 사용 가능한 후보가 있으면 fallback 배정을 한다. 반면 다른 계정이 gate 아래에 있으면, 곧 초기화되는 계정의 남은 양이 활용되지 않을 수 있다.

고정 비율을 즉시 소비 예측으로 대체하지 않는다. 먼저 예측만 기록하는 shadow 단계에서 다음 두 판단을 구별한다.

| 판단 | 필요한 증거 |
|---|---|
| 기존 세션만으로 초기화 전에 소진될 가능성이 충분히 높음 | 기존 수요의 **낮은 쪽** 추정도 남은 양보다 큼 |
| 기존 세션을 처리한 뒤에도 여유가 남을 가능성이 충분히 높음 | 기존 수요의 **높은 쪽** 추정과 버퍼를 빼도 남음 |
| 두 구간이 겹침 | 불확실함. 확실히 소진되거나 남는다고 표시하지 않음 |

account `a`, window `w`에 대해 남은 양의 추정 구간을 `[R_L, R_U]`, 유효한 예측 구간 동안 기존 작업이 소비할 양을 `[D_L, D_U]`, 이미 배정한 새 작업의 예약 추정을 `Q_U`, 추가 오차 여유를 `M`으로 둔다. 단위는 해당 window의 사용률 percentage point다.

- `D_L > R_U`이면 기존 작업만으로도 소진될 위험이 충분히 높다는 근거가 된다. 여기에 새 세션을 더 얹을 이유가 되지 않는다.
- 보수적인 잔여 추정은 `S = R_L - D_U - Q_U - M`이다. `S > 0`이어도 새 세션 전체를 끝까지 처리할 수 있다는 보장은 아니다. 예상 배정 수요와 모든 관련 window를 추가로 확인한다.
- 이것은 통계적 의사결정 모델이다. 엄밀한 지출 상한이나 용량 예약으로 표시하지 않는다.
- 필요한 것은 평균의 신뢰구간이 아니라 미래 실제 소비의 예측 구간이다. shadow 결과로 구간의 포함률을 보정하기 전에는 숫자에 임의의 확률 보장을 붙이지 않는다.

예를 들어 2시간 뒤 초기화되고 20%가 남았다면, 기존 수요 상한 8%와 버퍼 3%를 제외한 여유 추정은 9%다. 새 세션의 보수적 수요가 이를 넘으면 다른 계정을 고려한다. 기존 수요가 25%라는 점 추정 하나만으로 확실한 소진을 선언하지 않는다. 구간이 15–35%라면 불확실하고, 낮은 쪽도 23%라면 추가 배정을 피할 근거가 강하다.

예측은 다음 조건을 만족해야 한다.

- 5시간·주간뿐 아니라 실제 존재하는 30일 등 유효 window의 제한을 무시하지 않는다. 다만 현행 새 세션 gate는 30일 창을 일반화해 처리하는 기능이 아니다. window의 account/model 범위·기간·reset 의미가 확인되어 예측을 지원할 때만 각각 계산하고, 미지원이면 확대 배정을 끈다. 가장 부족한 제약을 따르고 없는 window를 만들지 않는다.
- 사용률 증분은 토큰·달러와 같은 단위가 아니다. 모델·캐시·출력·서비스 내부 가중치가 다르므로 단순 환산하지 않는다.
- 계정 단위 관측에 외부 트래픽과 동시 세션이 섞인다. 이를 요청별 실제 소비량으로 정확히 나눴다고 주장하지 않는다.
- 성공한 폴링·응답 관측 시각, 지연·양자화, 부분 window, reset 세대, 모델·부하 변화를 보존한다. reset 전후의 차이를 음수 소비나 새 증가율로 학습하지 않는다.
- 관측이 없거나 오래됐거나 적으면 예측을 사용하지 않는다. 기존 gate와 여유 기반 fallback을 유지한다. 불확실함을 사용량 0으로 바꾸지 않는다.
- 마지막 관측 이후 실행 중이거나 이미 끝났지만 미반영인 소비를 별도로 고려한다. 같은 소비를 잔량 오차·기존 수요·새 예약에 중복 차감하지 않는다. 정확한 귀속을 확인할 수 없으면 제한적인 과예약을 감수하고 자동 확대를 억제한다.
- 장기 reset까지 짧은 관측 속도를 그대로 곱하지 않는다. 검증된 예측 지평을 넘으면 구간을 넓히고 낮은 신뢰도로 표시하거나 기존 배정으로 돌아간다.
- 새 배정 예약은 서비스별 선택 잠금과 함께 처리한다. 성공/실패/취소/정책 변경 시 갱신하고 실제 관측과 중복 차감하지 않는다.
- 계정 이동으로 생긴 cache-cold 재전송이 예측을 다시 바꿔 이동을 부르는 순환을 막는다. 예측은 새 세션 배정에만 사용하고 기존 세션 이동 사유로 쓰지 않는다.

## 6. 추가 크레딧 설명

`구독 이용 한도`는 요금제에 포함된 사용량이다. `추가 크레딧`은 그와 별도로 쓸 수 있는 잔액이다. 잔액이 있는 것, quota-baton에서 허용한 것, 실제로 사용 중인 것은 다르다.

현재 99% 관측 차단은 추가 사용 구간을 피하려는 예방책이다. 관측 사이의 큰 요청까지 포함해 상류의 추가 차감을 0으로 강제하는 기능은 아니다. 실제 지출 차단을 약속하려면 상류에서 강제하는 제어를 확인해야 한다. 전환 허용이나 다른 계정 부재가 크레딧 허용을 대신하지 않는다.

설명 예시는 다음과 같다.

- `현재 계정 유지: 사용할 수 없으면 멈춥니다.`
- `구독 한도 소진 시 다른 계정으로 전환: 캐시 적중이 줄어들 수 있습니다.`
- `일시적인 요청 속도 제한입니다. 같은 계정에서 기다리고 있습니다.`
- `추가 크레딧 사용 허용: 구독 한도 이후 잔액이 차감될 수 있습니다.`
- `이 세션은 자동 전환이 꺼져 있어 멈췄습니다. 계정 A의 한도는 14:30에 초기화될 예정입니다.`

## 7. 검증 범위와 남은 예측 작업

다음은 구현의 합격 조건이다. 실제 실행 결과와 한계는 마일스톤 보고서에 기록하며, 예측 배정은 관측 전용이다.

| 합성 시험 | 확인할 결과 |
|---|---|
| 계정 유지 + quota/auth/payment/pause + HTTP/WS reconnect | 다른 계정 전송 0회, 명시적 중단, 토큰 복구 안전성 유지 |
| A/B의 rate를 교대로 발생시키고 활성 그룹 수도 변경 | 그룹·제공자별 재량적 예산, 체류·재방문 제한을 지키고 보호 veto 시 유효한 표시를 유지함 |
| 이동 표시 뒤 대상이 중지·혼잡·rate 상태로 변경 | 전송 직전 조건 재확인, 부적격 이동 0회 |
| 여러 출발 계정이 같은 대상으로 동시에 이동 | 도착지 예약을 합산하고 과예약하지 않음 |
| 오래된 idle WS와 실제 응답 중 WS | 캐시/LRU pin과 실제 활성 부하를 구별함 |
| 작은 WS delta 뒤 큰 full-input 재연결 | 작은 마지막 delta로 이동 비용을 과소평가하지 않음 |
| reset 시각 오차·관측 지연·동일 reset 반복 | 전체 deadline과 취소를 지키고 무한 hold가 없음 |
| 버퍼·부분 poll·외부 트래픽·모델 변경·reset rollover | 예측 신뢰도 저하와 fallback이 결정적으로 재현됨 |
| gate 아래 대안이 있고 초기화 직전 계정은 90% 초과 | shadow 비교가 낭비/강제전환 위험을 각각 기록함 |
| 응답 공개 후 오류 또는 보관 예산 부족 | 재전송 금지·원본 바이트 보존을 유지함 |
| 재시작·takeover·LRU 퇴출·자식 에이전트 | 루트 정책과 필요한 이동 예산을 잃지 않음 |

shadow 단계는 기존 배정을 바꾸지 않는다. 예측 구간의 실제 포함률, 초기화 시 남은 양, 강제 전환 수, 이동 뒤 rate 재발, 그룹별 왕복, 실제 제공된 cache-read/write/input/output 지표, 추가 전송 바이트, 대기 p50/p95를 측정한다. 누락은 unknown으로 남긴다. 단일 합성 시험이나 한 번의 200 응답을 제공자 호환성·비용 절감의 증명으로 쓰지 않는다. 로그에 원문 대화·인증·전체 경로를 넣지 않고 보존량을 제한한다.

전환 정책과 기본값, 이동 보호는 D20으로 승인되었다. 예측을 실제 배정에 활성화하는 기준은 별도 승인과 관측 근거가 필요하다. 기본 90/98% gate는 유지한다.
