개요와 범위

architecture §1 · §4 · decisions D1–D9 · D16

CLI는 quota-baton을 Anthropic이나 OpenAI 주소로 알고 요청을 보냅니다. quota-baton은 요청 내용을 그대로 두고 인증 정보만 고른 계정의 것으로 바꿔 실제 서버로 넘깁니다. 응답도 그대로 돌려줍니다.

하는 일

  • Claude Code(Messages API)와 Codex CLI(Responses API, WebSocket과 HTTP)의 요청 중계
  • 프로바이더별 계정 여러 개를 사용량을 보고 골라 쓰기, 새 세션을 계정에 나눠 배치
  • 한도, 로그아웃, 재로그인 필요, 결제 거절을 즉시 반영
  • 요청 속도 제한(429)은 같은 계정에서 기다려 흡수
  • 트레이에서 계정별 사용량과 상태 확인, 로그인과 일시정지
  • 클라이언트 설정을 기록하고 되돌릴 수 있게 바꾸는 컷오버 도구

하지 않는 일

  • 프로토콜 번역 (예: Codex에서 Claude 모델 쓰기)
  • 클라이언트 위장: TLS 지문, 헤더, 기기 정보 바꾸기
  • API 키 사용. 과금되는 자격 증명은 풀에 들어오지 않음 (D16)
  • Orca, ~/.codex 등의 토큰 가져오기 (CPA는 연결 모드로만 가져옴)
  • 세션 총수 조절, 대기열, 멈춘 세션 재개 (오케스트레이터 몫, D14)
  • 원격 접속, 다중 사용자, 자동 업데이트, 오케스트레이터 전용 API

메모리를 줄일 수 있는 이유

architecture §2.2 · 근거 R6(Codex 0.162.1 소스) · R7(실측)

프롬프트 캐시는 OpenAI와 Anthropic 서버에 있습니다. 프록시가 바이트를 바꾸지 않고 세션을 같은 계정에 두기만 하면 캐시는 유지되고, 프록시가 따로 저장할 것은 없습니다. 대화 전체는 Codex CLI가 직접 들고 있습니다. 연결이 끊기면 Codex가 알아서 대화 전체를 다시 보냅니다.

이전 프록시의 메모리는 설정 때문이었습니다. Codex 계정에 WebSocket 모드가 꺼져 있어서 WebSocket 손님을 HTTP 방식으로 처리했고, 그러느라 열린 연결마다 대화 전체를 들고 있었습니다.

실측 기간은 이전 프록시 로그 126시간입니다. quota-baton이 붙드는 것은 연결당 작은 버퍼, 세션당 수십 바이트의 계정 바인딩, 첫 응답 전까지의 요청 본문 1부뿐입니다. 실제 프로필로 47시간 돈 코어는 10MiB를 썼습니다(최종 검수).

설계 원칙

architecture §3
P1그대로 전달

인증 헤더만 바꿉니다. 본문 예외 목록(C4)은 비어 있습니다. 예외를 추가하려면 0단계 실험 근거, 테스트, 사용자 승인이 있어야 합니다.

P2메모리 상한

본문은 1부, WebSocket 메시지는 쓰는 동안만 둡니다. 공유 예산 384MiB를 넘으면 읽기를 멈추고, 1GiB 가드에 걸리면 새 요청을 받지 않습니다.

P3코어는 안정, 나머지는 자유

트레이, 설정, 계정 변경이 진행 중인 대화를 끊지 않습니다. 업그레이드는 넘겨받기 방식으로 합니다.

P4정직한 계정 상태

서버가 보낸 명시적 오류 코드로만 상태를 바꿉니다. 토큰 만료 시각만으로는 판단하지 않습니다.

P5사용량과 캐시 인식

진행 중 대화는 세 경우에만 옮깁니다. 계정을 쓸 수 없을 때(강제), 캐시가 이미 식었고 그 계정이 게이트를 넘었거나 가득 찼을 때(식은 시점), 계정에 세션이 몰려 다른 계정에 여유가 있을 때(과부하, 제한적).

P6토큰 주인은 하나

자체 OAuth 로그인 계정과 CPA에서 가져온 계정만 씁니다. 가져온 계정은 CPA가 계속 갱신하고 quota-baton은 따라 읽기만 합니다. 갱신하는 쪽은 언제나 하나뿐이고, 새 토큰은 저장한 다음에 씁니다.

P7작은 범위

프로바이더는 Claude와 Codex 둘, 자격 증명은 구독 OAuth만 다룹니다. 번역은 하지 않습니다.

P8로컬 전용

127.0.0.1에만 열고, 클라이언트 키와 Host·Origin을 검사합니다. 관리 포트는 따로 둡니다.

구성 요소

architecture §4 · §10–§12 · contract C11–C12 · user-guide

프로그램 (Rust, 실행 파일 2개)

  • quota-baton serve [--takeover]: 코어. 데이터 포트 10200, 관리 포트 10201
  • quota-baton status: 코어와 계정 상태
  • quota-baton accounts login · list · pause · resume · disable · enable · refresh-usage · import cpa
  • quota-baton wire · unwire: 컷오버 도구. 기본은 미리보기
  • quota-baton-tray: 트레이. 종료할 때 "트레이만" 또는 "프록시까지" 선택

트레이 플라이아웃 (좌·우클릭)

  • 계정마다 상태 칩: 사용 중, 준비됨, 한도(재설정 시각), 재로그인 필요, 일시정지, 비활성, 속도 조절 중
  • 5시간·주간 사용량 막대와 리셋 시각, 활성 세션 수 / 분산 임계치
  • 재로그인, 일시정지·재개, 비활성화, "새 대화 받지 않기", "유료 크레딧 허용", 사용량 새로고침, 계정 삭제
  • 계정 추가, 설정 폴더, 로그, 종료
  • 지금 있는 알림은 "코어 재시작" 하나입니다. 상태 배지, 다크 테마, 재로그인·연결 토큰 만료·한도·전 계정 소진·조직 거부·폭주 알림은 R1에서 추가합니다(architecture §10).
  • 코어가 응답하지 않으면 트레이가 다시 띄웁니다. 시작 즉시 실행과 10초 점검 주기는 R1에서 명세대로 맞춥니다.

데이터는 %LOCALAPPDATA%\quota-baton\에 둡니다. 설정(config.toml), 계정 파일(토큰은 DPAPI 암호화), 세션 바인딩, 사용량 스냅숏, 요청 기록(내용 없이 메타데이터만, 30일), 로그(비밀값 마스킹)가 들어갑니다.

요청 한 건의 경로

Claude Code의 모든 요청과 Codex의 HTTP 요청이 이 경로를 탑니다. 계정을 바꿔 재시도할 수 있는 시점은 커밋 전까지입니다.

WebSocket 중계 (Codex)

architecture §9 · contract C6 13행 · C6.3 · 근거 R6

Codex는 대화(스레드)마다 WebSocket 연결 하나를 열어 여러 턴 동안 씁니다. quota-baton은 클라이언트 연결 하나를 OpenAI 연결 하나에 1:1로 잇고, 그 연결은 끝날 때까지 한 계정에 고정합니다.

  • 연결을 먼저 맺고 답합니다. 모든 계정이 한도면 연결 요청 단계에서 429 usage_limit_reached로 답하고, 쓸 계정이 없으면 400으로 답합니다. 둘 다 Codex가 재시도하지 않는 응답이라 재시도 횟수를 소모하지 않습니다.
  • 속도 제한 오류는 위 그림을 타지 않습니다. 응답 시작 전 속도 오류가 오면 같은 업스트림 소켓에 마지막 response.create를 다시 보내고, 소켓이 닫혔으면 같은 계정으로 새로 연결합니다. 오류에 재시도 조언이 있으면 그대로 넘기고, 그 밖에는 1012로 닫되 재연결 제외를 걸지 않아 같은 계정으로 돌아옵니다. 연결 요청 단계의 대기는 10초를 넘지 않습니다(Codex 연결 제한 15초).
  • 426은 쓰지 않습니다. Codex는 426을 받으면 그 세션을 바로 HTTP로 고정합니다.
  • HTTP로 흉내 내는 모드가 없습니다. WebSocket 손님은 항상 WebSocket으로 잇습니다. 이전 프록시의 메모리 문제를 만든 모드라 켜고 끌 설정 자체를 두지 않았습니다.
  • 연결 협상은 구간마다 따로 합니다. 연결용 헤더(Sec-WebSocket-*)는 복사하지 않습니다. 압축은 두 구간 모두 쓰지 않습니다. OpenAI 구간은 쓰는 라이브러리(tokio-tungstenite 0.28)에 permessage-deflate가 없어, 켜는 설정을 주면 시작을 거부합니다(D12).
  • 큰 메시지: 메시지와 프레임 한도를 모두 192MiB로 둡니다. 공유 예산이 차면 그 연결의 읽기를 멈춰 메모리 대신 TCP가 기다리게 합니다.
  • 쉬는 연결: 30분 쉬면 닫습니다(서버는 60분). Codex는 다음 요청 때 조용히 다시 연결합니다.

계정과 토큰

architecture §6 · contract C5 · C10 · decisions D5

로그인과 저장

  • 계정은 자체 OAuth 로그인(PKCE)으로 추가하거나 CPA에서 가져옵니다. 로그인 콜백은 127.0.0.1과 ::1에서만 받고, 끝나면 바로 닫습니다.
  • CPA에서 가져온 계정은 연결 모드입니다. CPA가 갱신하고 quota-baton은 그 파일을 다시 읽어 따라갑니다. 지금 실제 계정 8개가 모두 연결 계정입니다(프로바이더당 2개 활성).
  • 갱신을 넘겨받는 인수 모드는 만들지 않았습니다. CLI와 관리 API는 거부합니다. 그래서 연결 계정이 있는 동안 CPA는 갱신 담당으로 계속 돌아야 합니다. 만들지는 사용자 결정입니다.
  • Codex 로그인은 1455 포트를 씁니다. codex login이 그 포트를 쓰고 있으면 안내만 하고 멈춥니다.
  • 토큰은 DPAPI로 암호화하고, 임시 파일에 쓴 뒤 교체하는 방식으로 저장합니다. 독점 잠금을 쥔 코어만 갱신하고 저장합니다.

갱신 규칙 (직접 로그인 계정)

  • 남은 수명이 20% 아래면 미리 갱신합니다. 401이 오면 실패한 토큰이 현재 토큰일 때만 갱신합니다.
  • 보내기 전에 "결과 불확실" 표시를 저장하고, 새 토큰은 저장한 다음에 씁니다. 갱신 토큰은 한 번만 쓸 수 있기 때문입니다.
  • 종료 코드(refresh_token_invalidated 등)면 재시도 없이 재로그인 필요로 바꿉니다.
  • 전송이 끊겨 결과를 모르면, 지금 토큰으로 계속 쓰다가 다음 갱신 시점에 한 번 더 시도합니다.
  • 연결 계정은 토큰 엔드포인트를 부르지 않습니다.

사용자 설정은 상태와 별개입니다. 일시정지하면 진행 중인 대화도 다음 요청 때 다른 계정으로 옮깁니다. 비활성화하면 선택도 사용량 조회도 하지 않습니다. "새 대화 받지 않기"는 새 대화만 막고 진행 중인 대화는 그대로 둡니다. 유료 크레딧은 "허용"을 켠 계정만 씁니다.

계정 선택

contract C7 · C7.1 · C8 · decisions D11 (블라인드 패널) · D15

대화를 다른 계정으로 옮기면 그다음 한 턴은 캐시 없이 대화 전체를 다시 읽습니다. Claude Opus 5.5 기준으로 캐시 읽기는 입력 가격의 0.05배, 캐시 쓰기는 1.25배(5분) 또는 2배(1시간)라서, 옮긴 한 턴이 평소 턴 25–40번 분량의 입력 비용을 씁니다. Codex는 이전 기록상 전환 후 캐시 적중률이 88%(평소 95%)였습니다.

세션 구분

  • Claude Code: X-Claude-Code-Session-Id 헤더를 씁니다(V1에서 확인). 서브에이전트는 부모 계정을 물려받습니다. 헤더가 없으면 본문 끝 64KiB에서 metadata.user_id를 찾고, 그것도 없으면 마지막에 쓴 계정에 둡니다.
  • Codex: session-id 헤더를 씁니다. 서브에이전트도 루트 세션 ID를 보내므로 같은 계정에 묶입니다.

사용량 추적

  • 응답 헤더(anthropic-ratelimit-unified-*, x-codex-*)와 WebSocket 이벤트에서 공짜로 읽습니다.
  • 조회 API(wham/usage, Claude 사용량)는 계정당 최소 5분 간격으로 부릅니다. 후보 계정과 트레이가 열렸을 때, 대기 중인 계정은 매시간, 모든 계정 소진을 알리기 직전에 부릅니다.
  • 사용량 100%나 크레딧 사용 직전(99%)이면 서버가 거절하기 전에 미리 대기 상태로 둡니다.

새 대화와 진행 중 대화 규칙은 Opus 5.5, Fable 5.1, Codex(gpt-6.1-sol)가 서로 모른 채 같은 질문지에 답한 결과입니다(D11). 우선순위 목록은 두지 않고, 수동 배치 설정은 "새 대화 받지 않기"뿐입니다. 분산 임계치와 과부하 재배치는 사용자 지시로 D15에서 더했습니다.

속도 제한과 세션 분산

contract C6.3 · C7.1 · decisions D14 · D15

요청 속도 429는 계정이 너무 빨리 불리고 있다는 뜻이지, 할당량이 바닥났다는 뜻이 아닙니다. 세션을 옮기면 캐시를 잃고 전체 문맥을 다시 보내므로, 옮긴 계정까지 속도 제한에 걸립니다(10-14 이전 프록시 사고). 그래서 속도 429는 같은 계정에서 흡수하고, 세션은 처음부터 계정에 나눠 배치합니다.

계정별 속도 조절 (C6.3)

  • 속도 429를 받은 적이 없는 계정에는 관문이 없습니다. 간격도 동시 요청 제한도 없습니다.
  • 속도 429가 오면 그 계정에 대기 창을 엽니다: 서버 Retry-After와 2단계초 중 긴 쪽, ±20%. 단계는 최대 5이고, 429 없이 한 간격이 지날 때마다 하나씩 내려갑니다.
  • 조절 중에는 요청을 도착 순서대로 간격(250ms에서 최대 5초)을 두고 하나씩 내보냅니다.
  • 60초를 기다린 요청은 한 번 그대로 보내고 응답을 그대로 전달합니다. 프록시가 429를 지어내지 않습니다.
  • 새 세션 배치는 조절 중이 아닌 계정을 먼저 고릅니다. 묶인 세션은 조절 때문에 옮기지 않습니다.
  • 계속되는 제한 아래에서 Codex HTTP 한 턴은 약 5–6분 버팁니다. 그 뒤는 세션 수를 줄이는 오케스트레이터의 몫입니다.

역할 분리 (D14)

  • quota-baton: 계정 문제(한도·인증·권한·결제)의 전환, 같은 계정에서 속도 제한 흡수, retry-after를 붙인 원래 형식 오류, 계정 간 세션 분산
  • 클라이언트(Codex, Claude Code): 자체 턴 내 재시도. 그대로 둠
  • 오케스트레이터(/goal 감독): 전체 세션 수, 멈춘 세션을 언제 재개할지(지터를 둔 대기, 같은 세션에서 재개, 한꺼번에 재개하지 않기)
  • quota-baton은 세션을 줄 세우거나 거절하지 않습니다. 계정별 활성 세션 수는 관리 API와 트레이로 보여 줍니다.
진행 중 세션을 옮기는 경우언제비용
강제묶인 계정을 쓸 수 없게 됨: 한도, 갱신 후에도 인증 실패, 권한·결제 거절, 일시정지·비활성다음 한 턴 캐시 없음
식은 시점1시간 이상 쉬었고, 지금 계정이 게이트를 넘었거나 활성 세션이 임계치 이상캐시는 이미 식어 추가 비용 없음. 이전 속생각만 잃음
과부하위 그림의 조건에서 표시된 그룹만, 다음 요청 경계에서캐시 손실을 감수 (사용자 지시, D15)

옮기지 않는 경우: 속도 429 하나만으로, 사용량 게이트만으로, 스트림이나 요청이 진행 중일 때, 여유 있는 계정이 없을 때. 모든 이동은 이유, 출발·도착 계정, 요청 크기, 다음 턴의 캐시 결과와 함께 기록합니다.

계정을 넘길 때 대화가 이어지나

architecture §2.2 · §16.1 V2 · contract C4 · decisions D10

대화 데이터는 거의 전부 평문이라 어느 계정이든 읽을 수 있습니다. 예외는 모델이 답하기 전에 한 생각입니다. 서버는 이 생각을 자기만 열 수 있는 봉인된 데이터(Codex의 encrypted_content, Claude의 서명된 thinking)로 돌려주고, CLI는 그것을 매 턴 다시 보냅니다.

Codex와 Claude Code는 이 봉인 데이터를 매 턴 그대로 다시 보내고, 직접 빼는 일이 없습니다. quota-baton도 똑같이 그대로 전달합니다(D10).

V2 실험 결과 (2026-10-13)

  • 계정 A의 봉인 데이터를 계정 B로 보내면 200입니다. 서버가 오류 없이 무시합니다. 입력 토큰 수가 데이터를 뺀 경우와 같았고, 도구 호출 도중의 턴에서도 같았습니다.
  • 자기 계정에서 1바이트를 변조하면 400입니다. 서버는 자기가 만든 것은 검증하고, 남이 만든 것은 버립니다.
  • WebSocket(M3 이후)에서도 같았습니다. 계정을 바꾼 턴이 정상으로 이어졌습니다.
  • 잃는 것은 이전 턴의 속생각과, 넘긴 직후 한 턴의 캐시뿐입니다.

그래서

  • 조각을 빼거나 고치는 기능(E1–E3)과 거절 시 재전송 안전장치(E2r)는 만들지 않았습니다.
  • 남은 위험은 Codex 압축 요약입니다. 이전 프록시 로그에 다른 계정에서 거절된 듯한 기록이 3건 있고, 이 경우는 실험하지 못했습니다. 빼면 앞 대화가 사라지므로 빼는 방법은 없습니다. 대신 세션을 원래 계정에 오래 묶어 두어 피합니다.
  • 요청 기록에 서버 오류 코드를 남겨, 서버 동작이 바뀌면 드러나게 합니다.

무중단 교체

architecture §14 · contract C11

새 버전으로 바꿀 때 진행 중인 대화를 끊지 않습니다. 설정 파일과 계정 변경은 재시작 없이 바로 반영됩니다.

  1. 새 코어가 serve --takeover로 시작해 지금 코어에 넘겨 달라고 요청합니다.
  2. 지금 코어는 토큰 갱신과 파일 쓰기를 멈추고, 세션 바인딩을 넘긴 뒤 포트를 닫고 토큰 잠금을 놓습니다.
  3. 새 코어가 잠금을 쥐고 계정을 읽은 다음 포트를 엽니다.
  4. 지금 코어는 진행 중인 HTTP 스트림을 끝까지 보내고, WebSocket은 현재 응답이 끝나면 닫습니다(1001).
  5. 할 일이 없어지거나 30분이 지나면 지금 코어가 종료합니다.

WebSocket이 6초 넘게 끊기면 Codex 세션이 HTTP로 고정되므로, 포트를 넘기는 공백은 밀리초 단위여야 합니다. M3 실험에서 지금 코어가 받은 소켓을 쥔 채로도 새 프로세스가 0.58–0.81ms 만에 같은 포트를 열었습니다. 그래서 소켓을 통째로 넘기는 방식은 쓰지 않습니다. 교체 전 과정은 M7a에서 프로세스 단위로 시험했고, 24시간 부하 시험 중간에도 교체를 한 번 넣어 통과했습니다. 과부하 표시와 429 이력은 넘기지 않습니다.

컷오버

architecture §17 M8 · user-guide · decisions D5 · D9

실사용 클라이언트를 quota-baton으로 옮기는 일은 사용자가 정합니다(D9). 도구는 준비되어 있고, 아직 실행하지 않았습니다. 그 전에도 실제 프로필로 코어(10200·10201)와 트레이를 띄워 계정별 사용량을 보는 대시보드로 쓸 수 있습니다. 이때 클라이언트는 연결되지 않습니다.

quota-baton wire

  • 옵션 없이 실행하면 미리보기입니다. 바꿀 파일과 값을 비밀값을 가린 채 보여 줍니다. --apply일 때만 바꿉니다.
  • 적용 조건: 코어가 정상이고, 프로바이더마다 지금 쓸 수 있는 계정이 하나 이상.
  • 바꾸는 것: Codex 기본 홈의 openai_base_url(herdr shim 때문에 맨 위 섹션 유지)과 CPA provider 주소, model_catalog_json 제거(실시간 모델 목록 사용), Claude 설정의 ANTHROPIC_BASE_URL과 인증 값. 기존 provider id는 그대로.
  • 원래 값은 DPAPI로 암호화한 journal에 남기고, 파일은 원자적으로 씁니다.
  • 선택: --autostart(트레이 로그온 자동 시작), --detach-chatgpt-session-homes(herdr session-homes.json의 ChatGPT 세션 홈 분리), --disable-cpa-tasks(CPA 예약 작업 끄기). 마지막 옵션은 연결 계정이 있는 동안 쓰면 안 되고, R1에서 그 경우 거부하도록 바꾸고 있습니다.

quota-baton unwire와 범위

  • journal로 원래 값을 되돌립니다. 역시 미리보기가 기본이고 --apply로 실행합니다.
  • 사용자가 그 사이 고친 파일은 덮어쓰지 않습니다. --force를 줄 때만 되돌립니다.
  • .codex-acct 홈은 연결도 분리도 하지 않고 보고만 합니다.
  • Orca 홈은 연결하지 않습니다. 옛 세션이 Orca 홈에서 재개되면 계속 CPA를 씁니다.
  • CPA는 지우지 않습니다. 연결 계정의 토큰 갱신 담당으로 계속 돌아야 합니다. CPA를 완전히 끄려면 계정을 직접 로그인으로 바꾸거나 인수 모드를 만들어야 합니다.

사용자 결정 대기

  • 컷오버 실행: wire 미리보기를 보고 정합니다. 적용할 때 Claude 활성 계정 중 여유가 있는 계정이 있어야 합니다(10-16 점검 때 두 활성 Claude 계정이 주간 100%로 10-19까지 대기였음).
  • 인수 모드: 만들지 않으면 CPA는 연결 계정의 토큰 갱신 담당으로 계속 돌아야 합니다. 만들면 CPA가 더는 그 계정을 갱신할 수 없게 한 뒤에만 넘겨받습니다(D5).
  • O13 계정별 모델 권한: 계정마다 쓸 수 있는 모델이 다릅니다(10-13 gpt-daybreak-blue-latest는 한 계정에만 있음). 지금은 틀린 계정이 400 모델 미지원으로 답하면 다른 계정으로 넘기고 그 모델만 6시간 제외합니다(선택지 4). 다른 선택지: 모든 계정 모델 목록의 합집합 표시, 모델을 보고 계정 고르기, 트레이의 수동 목록.
  • D16 확인: 설계 담당이 정했고, decisions.md는 "확정"을 사용자 결정으로 정의합니다. O14(API 키와 우선순위)는 D16으로 정리되었습니다.

남은 질문

  • O10 로그인 영향: quota-baton 직접 로그인이 CPA의 같은 계정 로그인에 영향을 주는지. 토큰 폐기가 생기는지 지켜봅니다.
  • O11 HTTP 요청의 출처: 이전 프록시에 온 Codex HTTP 요청 9.9만 건을 누가 보냈는지. 요청 기록에 originator와 UA를 남겨 확인합니다.
  • O12 memories 경로: Codex의 memories 기능 경로는 기본으로 꺼져 있어 지원하지 않습니다(404). 필요해지면 추가합니다.
  • V8: 실제 Codex WebSocket 속도 제한의 모양은 실트래픽에서 관찰되면 기록합니다.

정리된 것: O9 모델 목록은 그대로 전달합니다(V7). 컷오버 때 model_catalog_json을 지워 Codex가 실시간 목록을 받게 합니다. V1과 V3가 위장 없이 통과해 D3와 부딪히는 지점은 없었습니다.
